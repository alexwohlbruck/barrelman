## Upgrading

```bash
cd /opt/barrelman
docker compose pull
docker compose up -d
```

`docker compose pull` refreshes every service's image in the **active profiles**. Barrelman's own three images follow `:latest`; every third-party image (Martin, GraphHopper, MOTIS, Pelias, Kokoro) is pinned by digest, so a pull never changes those. Moving one is a separate step, described under [upgrading pinned images](#upgrading-pinned-images).

Profile-gated services are skipped, which is easy to miss: on an instance running
the address geocoder, a plain `pull` fetches the six core images and leaves
`pelias/api` and `pelias/elasticsearch` on whatever they were. Name the profile
to include them:

```bash
docker compose --profile pelias pull
docker compose --profile pelias up -d
```

<Callout type="warn" title="An upgrade recreates containers, and takes imperative wiring with it">
Anything attached to the `barrelman` container from outside Compose is discarded
here. The usual casualty is a reverse proxy wired with
`docker network connect`: after `up -d` the container is no longer on the
proxy's network and every request 502s, while barrelman itself looks perfectly
healthy. Declare the attachment in an override file instead — see
[reverse proxy and TLS](/self-hosting/production#reverse-proxy-and-tls).
</Callout>

<Callout type="warn" title="MOTIS and GraphHopper bake data into a version-specific binary format">
Their on-disk timetable and routing graph are written by one engine version and rejected by another, so a pull that brings in a new major version leaves the engine unable to start:

```
tt: binary version mismatch [existing=34 vs expected=37], please re-run import
```

That is a job, not a restart:

```bash
docker compose exec -d barrelman-ops bash scripts/rebuild-motis.sh
docker compose exec -d barrelman-ops bash scripts/rebuild-graphhopper.sh
```

Both are pinned in `docker-compose.yml`, so this only happens when you move a pin yourself. Do it during a window where you can run the rebuild.
</Callout>

### Upgrading pinned images

Third-party images are pinned as `image:tag@sha256:…`. Docker resolves the digest and ignores the tag, which is there only to say which release the digest belongs to. Pelias publishes no release tags for most of its images, so those read `:master@sha256:…`. GraphHopper's pin is a digest alone: the June 2026 12.0 snapshot, from a nightly `:latest` whose October builds broke graph imports.

To move one:

1. Find the new release's digest. For a multi-architecture image this is the digest of the index, the one `docker buildx imagetools inspect` prints first:

   ```bash
   docker buildx imagetools inspect ghcr.io/motis-project/motis:2.11.4
   ```

2. Replace both the tag and the digest in `docker-compose.yml` (or `pelias/docker-compose.yml`), then pull and recreate that one service:

   ```bash
   docker compose pull motis
   docker compose up -d motis
   ```

3. Rebuild its data if the engine stores any:

   | Service | After moving the pin |
   |---|---|
   | `motis` | `scripts/rebuild-motis.sh`. The import runs with the image the server runs, so recreate the container first |
   | `graphhopper` | `scripts/rebuild-graphhopper.sh`, a full graph rebuild. Test a new build on a small region first |
   | `martin` | Nothing to rebuild. Check `docker logs barrelman-martin` for sources it dropped at startup |
   | Pelias | Usually nothing. A `pelias/schema` change can need a re-index, which is a multi-hour job |

4. Check the container's health with `docker compose ps`, then `/health` on the API.

To roll back, restore the old line and repeat step 2. For GraphHopper and MOTIS, run the rebuild again too, since the new engine may already have rewritten the data.

### Automating it

Watchtower can automate the pull, with three caveats.

- **It only manages containers on its own Docker host.** Watchtower watches the Docker socket it is given and nothing else, so an instance running on a different machine will never update your stack. Every host you want auto-updated needs its own.
- **Watchtower leaves pinned images alone.** A digest never points anywhere new, so Watchtower has nothing to pull for Martin, GraphHopper, MOTIS or Pelias. If you replace a pin with a floating tag, Watchtower will follow it, and for MOTIS and GraphHopper that means one day restarting onto an engine that rejects its data with nobody watching.
- **It will restart the stack in the middle of a job.** An import runs for hours — a replication update with post-processing has taken nearly twelve — while Watchtower polls hourly, so a push that lands mid-run kills it. See below.

### Not restarting mid-import

`docker-compose.yml` ships a `pre-update` lifecycle hook on `barrelman-db` and `barrelman-ops`. Watchtower runs it before it stops either container, and the hook exits 75 (`EX_TEMPFAIL`) if a job is running, which tells Watchtower to skip that container and ask again on the next poll. The update lands on its own once the job finishes.

Both containers need the gate. The worker runs the script, but the SQL runs inside the database container over the docker socket, so restarting either one ends the job.

The hook is inert unless Watchtower is started with `--enable-lifecycle-hooks`:

```yaml
services:
  watchtower:
    image: nickfedor/watchtower
    command: --cleanup --interval 3600 --enable-lifecycle-hooks
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
```

<Callout type="warn" title="Only 0 and 75 are safe exit codes">
Any other non-zero exit from a pre-update hook aborts Watchtower's entire update run, not just the one container. The shipped hook fails closed to 75 when it cannot reach the database, so an unreachable database postpones the update rather than wedging every container on the host.
</Callout>

Without the hook, a job killed this way sits `running` until the heartbeat reaper fails it about a minute after the worker disappears. The worker also hands its in-flight job back to the queue when it receives `SIGTERM`, so the replacement worker picks it up and re-runs it — every step of the import pipeline is idempotent — but that only helps if the database container survives.

Note that the original [containrrr/watchtower](https://github.com/containrrr/watchtower) has been unmaintained since November 2023, and its Docker client negotiates API version 1.25 — which Docker 29 refuses (`client version 1.25 is too old`), leaving the container dead on arrival. Use the maintained community fork, [nicholas-fedor/watchtower](https://github.com/nicholas-fedor/watchtower) (`nickfedor/watchtower`), which takes the same flags and the same `com.centurylinklabs.watchtower.*` labels.

## Keeping data fresh automatically

OSM, GTFS and GBFS all go stale, and the console can refresh them on a schedule
so you don't have to remember to. Open **Schedules**: a fresh install is seeded
with five entries, all **disabled** until you turn them on.

| Schedule | Default | What it does |
|---|---|---|
| OSM Update | Daily 03:00 | Applies the Geofabrik replication diff and re-runs incremental post-processing |
| Check for GTFS Updates | Daily 04:00 | Compares each feed's version against Transitland and re-imports only the regions that changed, then rebuilds MOTIS |
| Import GBFS Systems | Sunday 05:30 | Re-fetches the GBFS systems catalog |
| Rebuild Basemap | Sunday 06:00 | Re-renders the PMTiles basemap. Only needed when OSM Update has "Rebuild basemap" off |
| Refresh 3D Buildings | Sunday 09:00 | Refreshes the `buildings_3d` view. Only needed when OSM Update has "Refresh 3D buildings" off |

Any script under **Scripts** can be scheduled, with the same parameters you'd
fill in to run it by hand. Each entry takes a standard five-field cron
expression and its own IANA timezone, so `0 3 * * *` means 3am where you set it,
across daylight-saving changes.

A schedule fires by enqueueing an ordinary job. That's the point: a scheduled
import appears under **Jobs** marked *Scheduled*, with the same live log,
progress bar and cancel button as one you started yourself — not a line in a
logfile on the host. The **Schedules** page shows each entry's next and last
run, linking straight to that job.

Two separate things stop runs from colliding. First, the ops worker runs one job
at a time, so anything started while it is busy waits in a queue instead of
running alongside — **Jobs** shows a queued job's place in line and links to the
job it is waiting on. Second, scripts marked *One at a time*, which is every
long-running import including OSM Update, refuse a second run outright while one
is queued or running. A schedule that fires mid-run is recorded as skipped, with
the reason shown on its card, so a slow OSM import cannot stack up copies of
itself.

<Callout type="info">
Prefer a host crontab? It still works — but a script driven by `docker exec`
bypasses the job store, so nothing about that run appears in the console.
</Callout>

## Refreshing OSM data

To run one now instead of waiting for a schedule, use **Scripts** in the
console, or the command line. Incremental, via Geofabrik's replication feed:

```bash
docker compose exec -d barrelman-ops bash scripts/update-osm.sh
```

The feed is resolved from the region registry, so it follows `REGIONS` with
nothing to configure. Confirm what it will use before the first run:

```bash
docker compose exec barrelman-ops bun run src/config/regions.ts osm-replication
```

Not every extract publishes one. Re-download and re-import from scratch instead
with `UPDATE_MODE=full` — passed on the `exec`, because `.env` is not visible
inside the container:

```bash
docker compose exec -d -e UPDATE_MODE=full barrelman-ops bash scripts/update-osm.sh
```

If replication state was never initialized, run `scripts/init-replication.sh` first — also in the console, under **Scripts**.

<Callout type="warn" title="`.env` alone does not reach the importers">
Compose does not forward the host environment: a variable reaches
`barrelman-ops` only if its `environment:` block names it, and the scripts'
`source ../.env` cannot help — `.env` is excluded from the ops image, so there is
no `/app/.env` to read. `UPDATE_MODE`, `GEOFABRIK_URL` and
`GEOFABRIK_REPLICATION_URL` are named there as of August 2026; on an older file,
setting them in `.env` is a silent no-op. Check what actually arrived:

```bash
docker compose exec barrelman-ops env | grep -E 'UPDATE_MODE|GEOFABRIK'
```
</Callout>

### How often to run it

Whenever you like. The replication cursor lives in the database
(`planet_osm_replication_status`), not in a clock, so each run applies every
diff published since the last successful one. Skipping a week and
running once lands in the same place as running daily — the job just takes
longer. The seeded daily schedule exists to keep each run small, not because the
script depends on the interval.

Each chunk is applied to `region.osm.pbf` as well as to Postgres, so the
GraphHopper graph and the PMTiles basemap are both rebuilt from data that
matches the database. Both rebuilds are skipped entirely when a run finds no new
diffs.

The basemap matters here because it is the one output that cannot follow the
database on its own. Martin queries every `postgres:` source in
`martin-config.yaml` per request, so a diff reaches those tiles the moment it
lands; `basemap` is a static PMTiles archive, and PMTiles is a write-once format
that no tool can patch in place. `scripts/rebuild-basemap.sh` therefore
re-renders it with planetiler — a few minutes for a couple of US states. Set
`REBUILD_BASEMAP=0` on the update to skip it and enable the seeded weekly
**Rebuild Basemap** schedule instead.

### Large imports

On a country-sized import, three of the things an update triggers take hours:

- **Rebuild routing graph.** GraphHopper re-imports the whole extract, and street
  routing is down until it finishes.
- **Rebuild basemap.** planetiler re-renders the whole archive.
- **Refresh 3D buildings.** The `buildings_3d` view is rebuilt from every
  building in the database.

Turn all three off on the OSM Update schedule so the nightly run only updates
the database. Then enable the weekly **Rebuild Basemap** and **Refresh 3D
Buildings** schedules, and run **Rebuild GraphHopper** when you can afford the
routing downtime.

### Without middle tables

osm2pgsql-replication applies diffs through osm2pgsql's middle tables
(`planet_osm_nodes`, `planet_osm_ways`, `planet_osm_rels`). An import keeps them
because it runs with `--slim`, but they are large, about 13 times the size of
the extract. For the United States that is around 155 GB. A large install often
drops them after the import to get the disk back.

OSM Update still works without them. When `planet_osm_ways` is missing, the
update replicates through `region.osm.pbf` instead
(`scripts/replicate-extract.sh`):

1. It downloads the diffs since the last run and applies them to the extract.
2. It lists the objects the diffs touch, plus the ways and relations that
   contain them, and cuts those out of the patched extract with everything
   they reference.
3. It imports that small file with the normal flex style into a throwaway
   staging database.
4. In one transaction, it replaces the live rows of those objects with the
   staged ones and re-derives their search columns, intersections and parent
   context. Places inside a boundary that changed get new parent context too.

Nothing to set up. The first run starts from the replication header Geofabrik
writes into every extract (`osmosis_replication_sequence_number`), which is the
point the database was imported at. Each run then applies every diff published
since, up to 7 per transaction (**Diffs per cycle**). The cursor lives in its own
table:

```bash
docker exec barrelman-db psql -U barrelman -d barrelman \
  -c "SELECT base_url, sequence, data_timestamp FROM osm_replication_state;"
```

It needs memory and disk beyond a normal update:

- **Memory.** The osmium steps run inside `barrelman-db` and share its limit
  with Postgres. The update refuses to start below 4 GB
  (`BARRELMAN_DB_MEM_LIMIT`, 2 GB by default). For a country, allow 4 GB on top
  of what Postgres uses.
- **Disk.** A second copy of `region.osm.pbf` while it is patched, and a small
  staging database.

A transaction that would remove at least 1,000 rows and put back fewer than half
as many is rolled back. A normal diff mostly modifies objects, so a swap that
shrinks the table that much points at a broken extract. If the diffs really do
delete that much, run the update once with `REPLICATION_ALLOW_SHRINK=1`.

<Callout type="warn">
Geofabrik keeps roughly four months of diffs. A database left behind longer than
that can't be caught up incrementally — the next run fails on a sequence the
server has already dropped, and recovery means `UPDATE_MODE=full` followed by
`scripts/init-replication.sh`. Check how far behind you are with:

```bash
docker exec barrelman-db psql -U barrelman -d barrelman \
  -c "SELECT url, sequence, importdate FROM planet_osm_replication_status;"
```

```
                               url                                | sequence |       importdate
------------------------------------------------------------------+----------+------------------------
 https://download.geofabrik.de/north-america/us/colorado-updates/ |     4885 | 2026-08-19 20:20:48+00
```

Which table holds this depends on your osm2pgsql version, not on barrelman.
Version 1.8, which `barrelman-db` ships, writes `planet_osm_replication_status`.
Version 1.9 and later store the same thing in `osm2pgsql_properties`. On this
image, querying `osm2pgsql_properties` fails with
`relation "osm2pgsql_properties" does not exist`.
</Callout>

<Callout type="warn">
A database follows one replication feed. If `REGIONS` resolves to several, only
the first is replicated and the others stay at their last full import — the
script warns when it detects this. Use `UPDATE_MODE=full` to refresh all of them.
</Callout>

## Refreshing transit feeds

```bash
docker compose exec -d -e TRANSITLAND_API_KEY=<your key> barrelman-ops bash scripts/download-gtfs.sh
docker compose exec -d barrelman-ops bash scripts/rebuild-motis.sh
```

The second command is required every time. `motis server` never re-imports on its own.

`scripts/gtfs-watch.sh` wraps both, and only does the expensive part when a feed
has actually changed upstream — it compares each imported feed's version sha
against Transitland's. That's what the seeded GTFS schedule runs. Its first run
only records a baseline; it can't detect drift until it has a prior sha to
compare against.

## Backups

Only the database holds anything you cannot regenerate: accounts, API keys,
credits and usage, schedules and job history, region definitions and landmark
state. OSM, GTFS and the routing graphs are all rebuildable from source, so the
backup leaves them out and stays small. On a test instance the 20 state tables
dumped to 188 KB in about a second.

The tables are listed in `src/admin/backup-tables.ts`, with the reasons for
what is left out. Terms acceptance and the billing customer link are columns on
`accounts_users`, so they come along with it.

### Nightly backups

**Scripts → Back Up Database** (`scripts/backup-db.sh`) does the whole job:

1. dumps those tables with `pg_dump -Fc` to
   `/data/backups/barrelman-<UTC timestamp>.dump` in `barrelman-ops`
2. reads the dump back with `pg_restore --list` and fails unless every table's
   data is in it
3. uploads it when `BACKUP_S3_BUCKET` is set, and reads the object's size back
4. deletes local dumps older than `BACKUP_KEEP_LOCAL_DAYS` (7) and remote ones
   older than `BACKUP_KEEP_REMOTE_DAYS` (30), always keeping the newest

Any failure fails the job, so a broken backup shows up in **Jobs** the next
morning.

A fresh install comes with a disabled **Back Up Database** schedule at 02:15,
ahead of the 03:00 OSM update. Turn it on under **Schedules**. An instance that
already had schedules before this was added does not get the seed; create the
schedule yourself with cron `15 2 * * *`.

A dump on the same disk as the database is little use when the disk goes, so
set up a bucket. Any S3-compatible store works; the variables are in
[Configuration → Backups](/self-hosting/configuration#backups). For example, on
Hetzner Object Storage:

```dotenv
BACKUP_S3_BUCKET=barrelman-backups
BACKUP_S3_ENDPOINT=https://fsn1.your-objectstorage.com
BACKUP_S3_REGION=fsn1
BACKUP_S3_ACCESS_KEY_ID=...
BACKUP_S3_SECRET_ACCESS_KEY=...
```

Then recreate ops so it picks them up, and run one backup by hand to check:

```bash
docker compose up -d barrelman-ops
docker compose exec barrelman-ops bash scripts/backup-db.sh
```

The upload uses a pinned boto3, which `uv` downloads from PyPI into the
container's cache on first use. The cache does not survive a recreate, so the
first upload after every `docker compose up` of `barrelman-ops` needs to reach
PyPI. On a box without outbound access to it, that backup fails at the upload
step, with the local dump already written.

Give each instance its own `BACKUP_S3_PREFIX` (for example `barrelman/prod/`
and `barrelman/staging/`) when they share a bucket. Pruning and `latest` work
per prefix, so two instances on the default prefix would prune each other's
backups and restore each other's dumps.

Treat the bucket as credential storage. Lucia stores session IDs in the clear,
so the cookie value *is* the row's primary key in `accounts_sessions`, and the
dump also holds API-key hashes. Give the access key rights to this bucket
alone, and turn on the provider's object lock or versioning if it offers one.

### Restore drill

A backup that has never been restored is a hope. **Scripts → Restore Drill**
(`scripts/restore-db.sh`) restores the newest dump into a scratch database
next to the live one, named `barrelman_restore_<UTC time>`, and prints each
table's row count:

```bash
docker compose exec barrelman-ops bash scripts/restore-db.sh latest --drop-after
```

`latest` takes the newest dump in `/data/backups`, and falls back to the
newest in the bucket. Pass a file name or an object key instead to pick one:

```bash
docker compose exec barrelman-ops bash scripts/restore-db.sh barrelman/barrelman-20261104T021500Z.dump
```

Without `--drop-after` the scratch database stays for inspection, and the
script prints the command to drop it. `--target-db` picks the name, which must
start with `barrelman_restore`. The script marks each scratch database it
creates with a comment and only ever drops a database carrying that mark, so
it cannot remove another database on the same server by name.

Run a drill after setting up the bucket and again every few months. Pulling a
dump from the bucket on a different machine is the stronger test, since it is
the case backups exist for.

### Restoring for real

To put the backed-up tables back into the live database, stop the API so nothing
writes to them mid-restore, then run the restore with `--into-live` and a
confirmation variable set to the live database's name:

```bash
docker compose stop barrelman
docker compose exec -e BACKUP_RESTORE_CONFIRM=barrelman barrelman-ops \
  bash scripts/restore-db.sh latest --into-live
docker compose start barrelman
```

It replaces only the tables in the dump, in one transaction, so it applies in
full or not at all. The imported data is left as it is. This step is not
available from the console.

On a new server, bring the stack up, run the import, then restore: the import
recreates the geodata, and the restore brings back the accounts and settings.

### Whole-database dumps

A full dump is worth taking before an upgrade or a risky migration:

```bash
docker exec barrelman-db pg_dump -U barrelman -Fc barrelman > barrelman-$(date +%F).dump
```

It is dominated by data you can rebuild: on the Colorado instance it took
**3 m 30 s and produced 1.8 GB**, almost all of it `geo_places` and
`planet_osm_*`. A country-sized import makes this a tens-of-gigabytes job that
a re-import would reproduce anyway, so it is not a good nightly backup.

## Rotating secrets

Changing `BARRELMAN_API_KEY` in `.env` needs a recreate, not a restart — Compose bakes environment at container creation:

```bash
docker compose up -d --force-recreate barrelman
```

Account API keys (`brm_live_…`) are revoked from the console instead, and revocation is immediate: it evicts the verification cache directly rather than waiting out its TTL.
