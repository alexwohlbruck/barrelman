title: Importing data
description: Choose a region, run the import pipeline, and verify that every layer works.
---

A fresh database has no OSM data, so search returns nothing until you import some.

## Choose a region

Barrelman does not import "the world" by default. A **region** is a named bundle of data sources — an OSM extract, a transit search area, address files — and `REGIONS` picks which ones the pipeline pulls. Every importer resolves coverage from that one variable. There is no second place to configure it.

`REGIONS` is read by `barrelman-ops` (the importers), not by the API.

### Add a region by name

Fetch the boundary catalog once. It downloads Geofabrik's extract index — every published extract with its real political boundary, download URLs and ISO codes. No API key required.

```bash
docker compose exec barrelman-ops bun run scripts/fetch-boundaries.ts
```

Then in the console: **Regions → Add by name**, type a place, pick the match. That fills in the OSM extract URLs, the replication feed, a bounding box computed from the real boundary polygon, the Transitland search area, and US Census FIPS codes for address interpolation.

From the CLI, to see what matches without re-downloading the catalog:

```bash
docker compose exec barrelman-ops bun run scripts/fetch-boundaries.ts --skip-fetch --search colorado
```

Set the key in `.env` and recreate the worker so it sees the change:

```bash
sed -i 's/^REGIONS=.*/REGIONS=colorado/' .env
docker compose up -d barrelman-ops
```

<Callout type="warn" title="Create the region before naming it in REGIONS">
The two steps are independent. Naming a key no region defines fails closed:

```
Unknown region "colorado". Known regions: north-carolina, nyc-metro, global
```

Only `north-carolina`, `nyc-metro` and `global` ship in `config/regions.json`. Anything else has to be created first, in the console or via the admin API.
</Callout>

### Without the console

The console is a client of the admin API, so a scripted setup can do the same thing. Authenticate with an **admin-scoped API key** — sign in, create a key under **API keys**, and give it the `admin` scope (only administrators may grant it):

```bash
KEY=brm_live_…   # an API key with the `admin` scope
API=http://localhost:5001

curl -s -X POST -H "Authorization: Bearer $KEY" $API/admin/boundaries/refresh
curl -s -H "Authorization: Bearer $KEY" "$API/admin/boundaries?q=colorado"
curl -s -X POST -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"id":"us/colorado"}' $API/admin/boundaries/resolve
```

The last call returns `{"region":{…}}` and writes nothing. It already derives a
`key` from the boundary name (`us/colorado` → `colorado`); override it only if
you want a different one.

POST the **inner** object — not the `{"region":…}` envelope — to
`$API/admin/regions` to save it. A `201` with the saved region back is success;
`409` means that key already exists.

Unwrapping it needs a JSON tool. `jq` is not installed on a stock server and is
not otherwise required by this guide, so either install it or use the `python3`
that most distributions already ship:

```bash
curl -s -X POST -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"id":"us/colorado"}' $API/admin/boundaries/resolve > resolve.json

# with jq
jq '.region' resolve.json > region.json
# or without
python3 -c "import json;json.dump(json.load(open('resolve.json'))['region'],open('region.json','w'))"

curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  --data-binary @region.json $API/admin/regions
```

Confirm with:

```bash
docker compose exec barrelman-ops bun run src/config/regions.ts summary
```

### Confirm what is selected

```bash
docker compose exec barrelman-ops bun run src/config/regions.ts summary
docker compose exec barrelman-ops bun run src/config/regions.ts osm-extracts
```

Two things are deliberately **not** guessed for you: Who's-on-First place IDs, and any OpenAddresses coverage the repository listing does not actually show. The [region guide](/self-hosting/regions) has the field reference, how to build a region by hand (for example a metro area spanning three states), and why the import is *not* clipped to the bounding box.

## Run the pipeline

Each step depends on the one before it.

You can run every step from the console under **Scripts** — which gives you streamed logs, a confirmation gate on destructive tasks, and a job history — or from the CLI as shown here. They are the same jobs either way.

<Callout type="info">
Run these detached (`-d`) or under `tmux`. A state-sized import is tens of minutes; a country-sized one is hours. The console is the better option precisely because it survives your SSH session dropping.
</Callout>

### Step 1 — OSM to PostGIS and street routing (required)

```bash
docker compose exec -d barrelman-ops bash scripts/run-import.sh
```

This downloads each region's PBF, `osmium merge`s them into one extract, runs osm2pgsql inside `barrelman-db`, then does all the post-processing that makes search work: structured address extraction, GiST and GIN indexes, `codes` and `name_abbrev` precomputation, road intersections, parent-context spatial joins, and a full-text vector rebuild. Finally it rebuilds the GraphHopper graph.

Watch it:

```bash
docker exec barrelman-db psql -U barrelman -d barrelman -c "SELECT count(*) FROM geo_places;"
```

<Callout type="warn" title="`docker compose logs barrelman-ops` will not show this run">
Container logs carry the worker's own output — PID 1 — and a script started
with `docker compose exec -d` is a *different* process whose output goes
nowhere. The log stays empty on `[ops-worker] … polling for process jobs` for
the entire import, which reads exactly like nothing is happening.

Two ways to get real output:

- **Run it from the console**, under **Scripts**. The job runner captures the
  logs into the database, so **Jobs** shows streamed output, progress and an
  exit code — and it survives your SSH session dropping.
- **Redirect to a file** if you want to stay on the CLI:

  ```bash
  docker compose exec -d barrelman-ops \
    bash -c 'bash scripts/run-import.sh > /tmp/import.log 2>&1'
  docker compose exec barrelman-ops tail -f /tmp/import.log
  ```

A CLI run started with `-d` also has no completion signal. It is finished when
`docker top barrelman-ops` shows only `bun run src/worker/index.ts`.
</Callout>

Nothing below this line is required. Skip any of it you do not need.

### Step 2 — Transit (optional)

Three steps, in this order. All three are required, and each one needs the
previous to have **finished** — 2b imports the extract 2a writes, and 2c bakes
the feeds 2b downloads.

`-d` returns immediately, so running them as three separate detached commands
starts them all at once and the later two operate on inputs that do not exist
yet. Chain them in one command instead:

```bash
# 2a. Repair underground platform topology → region-transit.osm.pbf
# 2b. Download + import GTFS feeds. Needs GraphHopper from step 1 —
#     walking transfers between stops are routed through it.
#     Get a free key at https://transit.land/users/sign_up
# 2c. Rebuild the MOTIS dataset. REQUIRED — see below.
docker compose exec -d -e TRANSITLAND_API_KEY=<your key> barrelman-ops bash -c '
  { bash scripts/prepare-motis-osm.sh &&
    bash scripts/download-gtfs.sh &&
    bash scripts/rebuild-motis.sh ; } > /tmp/transit.log 2>&1
'

docker compose exec barrelman-ops tail -f /tmp/transit.log
```

The redirect has to be *inside* the container command — a `>` outside it applies
to the host shell, and a `-d` run has no output there to capture.

Running them one at a time is fine too — just wait for each to finish before
starting the next. In the console's **Scripts** view that is automatic: jobs are
claimed one at a time under an advisory lock, so a queued step cannot start
early.

<Callout type="warn" title="Why step 2c is not optional">
`motis server` only *serves* the pre-built dataset at `/data/data`. It never re-imports when the config or the feeds change, so a plain `docker restart` keeps serving the old schedules indefinitely and the new feeds never reach riders.

`rebuild-motis.sh` regenerates the config from the `gtfs_feeds` table, clean-rebuilds the timetable *and* street graph together — an in-place incremental import can leave the stop-to-street match index stale, which silently breaks routing to every stop — and restarts the server. The previous dataset is kept at `/data/data.prev` and restored automatically if the import fails.
</Callout>

Put `TRANSITLAND_API_KEY` in `.env` if you will refresh feeds regularly; it is already forwarded to `barrelman-ops`.

### Step 3 — Bikeshare (optional)

```bash
docker compose exec -d barrelman-ops \
  bash -c 'bun run import/import-gbfs-systems.ts > /tmp/gbfs.log 2>&1'
docker compose exec barrelman-ops tail -f /tmp/gbfs.log
```

Registers every GBFS **system** in the global catalog, then polls each one's feed
and keeps the **stations** that fall inside your region's bounding box.

<Callout type="info" title="`gbfs_systems` is a worldwide table, by design">
The catalog it reads (`systems.csv`) carries no coordinates, so systems cannot be
filtered by bbox — only the stations fetched from each feed can be. On the
Colorado run that meant **1,336 systems imported and 191 stations kept**:

```
 country_code | count
 FR           |   266
 DE           |   239
 US           |   170
```

Three of those 1,334 rows have coordinates inside Colorado. That is expected, not
a mis-import — filter on `gbfs_stations` when you want regional data.
</Callout>

It costs the same whatever your region size, since it walks the whole catalog
either way. Measured end to end on Colorado: **6 min 48 s**, with `200 failed` of
1,536 feeds — unreachable or dead endpoints are routine and not an error worth
chasing. Nothing else depends on this step, so skip it unless you need bikeshare.

### Step 4 — Addresses (optional, and much bigger than the rest)

Street addresses have no `name`, so they are not searchable in `geo_places`. Pelias fills that gap and folds address and street results into `/search`.

This is a separate stack behind Compose profiles — Elasticsearch alone wants a 1 GB heap — and provisioning its index takes **hours**, not minutes.

<Callout type="warn" title="This step wants the repository, not just the Compose file">
Unlike everything above it, Pelias is driven by files the curl install does not
fetch — `pelias/provision.sh`, `pelias/.env.example`, and the `pelias` CLI's
expectations about the directory it runs in. Clone the repo over your install
directory before starting:

```bash
cd /opt && git clone https://github.com/alexwohlbruck/barrelman.git barrelman-repo
cp -rn barrelman-repo/pelias/. /opt/barrelman/pelias/
```

Keep your existing `.env` and `docker-compose.yml`; you only need the `pelias/`
contents.
</Callout>

First regenerate the geocoder's coverage so it matches `REGIONS`, create the data
directory Elasticsearch will own, then start the two lean services:

```bash
docker compose exec barrelman-ops bun run scripts/generate-pelias-config.ts

# Elasticsearch runs as uid 1000 and cannot create its own directories under a
# root-owned bind mount.
mkdir -p pelias/data && sudo chown -R 1000:1000 pelias/data

docker compose --profile pelias up -d
```

<Callout type="warn" title="Skip the `chown` and Elasticsearch crash-loops">
`docker compose ps` shows `pelias_elasticsearch` restarting, and only its logs
say why:

```
ElasticsearchException[failed to bind service];
  nested: AccessDeniedException[/usr/share/elasticsearch/data/nodes];
```

`pelias_api` starts fine and answers queries regardless, so the stack looks
half-working: every geocode just returns nothing. Fix the ownership and
`docker restart pelias_elasticsearch`.
</Callout>

The generator reports exactly what it wrote and where. Check the path is the
**host** file — that is the copy the Pelias containers bind-mount, and a stale
one silently geocodes the wrong part of the world:

```
Wrote /app/pelias/pelias.json
  regions: colorado
  osm extracts: 1
  openaddresses files: 55
  wof places: 0, tiger states: 8
```

`wof places: 0` is normal — Who's-on-First IDs are one of the two fields the
region resolver deliberately does not guess.

<Callout type="warn" title="Older installs: the generator needs a Compose file from 2026-08 or later">
`barrelman-ops` only gained its `./pelias:/app/pelias` mount recently. Without
it the command above dies with `ENOENT … /app/pelias/pelias.json`, because
`pelias/` is excluded from the ops image and the container has no path to the
host's config. If you see that error, re-fetch `docker-compose.yml` and run
`docker compose up -d barrelman-ops`.
</Callout>

Then follow [`pelias/README.md`](https://github.com/alexwohlbruck/barrelman/blob/main/pelias/README.md) for the index build — budget hours, not minutes. Two things there are easy to miss and both fail silently:

- `vm.max_map_count` must be at least `262144`. Check first — Ubuntu 24.04 already ships `1048576` — and only raise it if yours is lower: `sysctl vm.max_map_count`, then `sudo sysctl -w vm.max_map_count=262144`.
- `pelias prepare polylines`, without which the `street` layer stays empty and street-name search returns nothing.

## Verify

Run all of these. Each one exercises a different layer, and a stack can pass the first and fail the rest.

```bash
KEY=brm_live_...   # or your BARRELMAN_API_KEY

# Liveness + database. "degraded" just means MOTIS has no timetable yet.
curl -s http://localhost:5001/health

# Credential
curl -s -H "Authorization: Bearer $KEY" http://localhost:5001/health/auth

# Search — the OSM import (step 1)
curl -s -X POST http://localhost:5001/search \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"query":"coffee","lat":39.7392,"lng":-104.9903,"radius":5000,"limit":5}'

# Reverse geocode — parent-context resolution (step 1 post-processing).
# THIS is the check that proves you imported the region you meant to.
curl -s -H "Authorization: Bearer $KEY" \
  "http://localhost:5001/geocode?lat=39.7392&lng=-104.9903"

# Street routing — the GraphHopper graph (step 1)
curl -s -H "Authorization: Bearer $KEY" \
  "http://localhost:5001/isochrone?lat=39.7392&lng=-104.9903&mode=walk&durations=600"

# Vector tiles — Martin against PostGIS. Source names come from
# martin-config.yaml (parchment_pois, parchment_roads, transit_platforms, …).
# Watch the size, not just the status — see the note below.
curl -s -o /dev/null -w '%{http_code} %{content_type} %{size_download}\n' \
  "http://localhost:5001/tiles/parchment_pois/12/853/1554?api_key=$KEY"

# Transit stops — the GTFS import (step 2b). Reads PostGIS, not MOTIS.
curl -s -H "Authorization: Bearer $KEY" \
  "http://localhost:5001/transit/stops?lat=39.7392&lng=-104.9903&radius=500"

# Transit routing — MOTIS's baked timetable (step 2c).
curl -s -H "Authorization: Bearer $KEY" \
  "http://localhost:5001/isochrone?lat=39.7392&lng=-104.9903&mode=transit&durations=1800"
```

The coordinates above are Denver, matching the `colorado` region this page builds.
Change them to your own region — and note which check actually detects a
mis-import:

| Endpoint | Queried outside your data |
|---|---|
| `/geocode` | `{"address":{},"hierarchy":[]}` — the honest, obvious failure |
| `/isochrone` | `Point not found:<lat>,<lng>` |
| `/search` | **still returns results** |

<Callout type="warn" title="A `/search` hit does not prove you imported the right region">
For a **text** query, `radius` biases ranking rather than filtering: text search
runs globally and re-ranks by proximity, so any place worldwide can still match.
Asked for `coffee` near Charlotte on a Colorado-only instance, `/search`
cheerfully returns Denver cafés — `distance_m` around `2186847`, i.e. 2,186 km
away. `radius` only becomes a hard `ST_DWithin` filter for category browse and
route-corridor searches, which carry no `query`.

So read `distance_m`, not just the result count, and use `/geocode` as the
region check.
</Callout>

<Callout type="warn" title="Low-zoom tiles are very large, and that is the shipped behaviour">
`parchment_pois` and `parchment_roads` are unfiltered tables between their
`minzoom: 10` and `maxzoom: 16`, so a low-zoom tile over a city serialises
everything inside it. Measured over Denver on a Colorado import:

| Zoom | `parchment_pois` | Time |
|---|---|---|
| 10 | 63 MB | 6.9 s |
| 12 | 14 MB | 0.7 s |
| 14 | 1.3 MB | 0.2 s |
| 16 | 92 KB | 0.05 s |

A `200` therefore proves nothing about usability. If you are pointing a real map
at this, either start your POI and road layers at z14, or narrow the sources in
`martin-config.yaml` — a `minzoom` closer to 14, or a filtered view that admits
only prominent features at low zoom. Left as-is, a zoomed-out map will pull tens
of megabytes per tile and stall the database behind it.
</Callout>

Those last two are worth running as a pair. Stops live in PostGIS while routing comes from MOTIS's own dataset, so a stack that skipped step 2c answers the first happily and returns nothing useful for the second.

Adjust the coordinates to somewhere inside your imported region — the most common cause of an empty-but-successful response is querying outside your data.

The console's **Dashboard** and **Data** views show the same thing visually: downstream service health for Postgres, MOTIS, GraphHopper and Martin, plus table sizes, coverage and freshness.
